# Erlang projects and hybrid workers

This extends the [v1 artifact handoff](libbeam-artifact-contract.md), not libbeam's execution profile. Packer compiles **trusted local projects** and packages original BEAM bytes; inspecting an artifact does not run its code, start OTP applications or verify Isolate admission. The current libbeam core admits selected Erlang BEAMs but not broad OTP services, including the process/GenServer and Elixir features used by the to-do example.

## Project adapters

1. **Mixed Mix project:** `mix midgard.build` or `mix packer.pack` compiles both `lib/**/*.ex` and Mix's ordinary `src/**/*.erl` project modules. The local app's BEAMs and compiled runtime Mix dependencies are included exactly once, with their original module names and app/version owners. Pure Erlang dependencies are allowed alongside pure Elixir dependencies. A declared source module which did not produce a matching BEAM must fail rather than silently disappear. The Midgard worker still exports `__midgard_call__(binary) :: binary` using the SDK; its Erlang helper modules can own state on normal OTP.
2. **Standalone rebar3 application:** run the Packer command from this checkout with an explicit `--project /path/to/rebar3-app --entry module --function handle --protocol raw.bytes.v1`. Packer invokes a trusted `rebar3 compile` (configurable executable for CI), identifies **one** application from its compiled `.app` metadata, and collects compiled project and dependency BEAMs from `_build/default/lib/<app>/ebin` and `_build/default/checkouts/<app>/ebin` together with app names/versions. Checkout dependencies report their compiled `.app` version but are not lockfile-pinned; a future immutable deployment pipeline must pin them independently. A missing `rebar3`, missing/ambiguous app, unresolved or missing module, native input, or unsupported dependency fails clearly; multi-application rebar3 umbrellas, NIFs and `priv` resources are not admitted. `mix packer.inspect PATH` works for either origin without needing Mix/rebar3 project source.

A standalone Erlang worker needs **no Elixir SDK**. Its declared entrypoint must export an arity-one function that accepts and returns bounded binaries. The simplest `raw.bytes.v1` echo fixture is deliberately *not* an HTTP server or a Midgard Request decoder. An Erlang worker which wants HTTP semantics must explicitly implement a compatible versioned byte protocol; no implicit Erlang-term encoding, Mix wrapper or full OTP service availability is assumed. A `packer.pack` default built for Elixir's `midgard.bytes.v1` must never silently label a raw Erlang function with that protocol.

## Module and dependency identity

The artifact remains an inspectable `manifest.json` plus raw `modules/<exact-name>.beam` files. Version 1 fields remain available to existing Elixir artifacts. Admit a conservative path-safe module-name subset: `Elixir.Name...` for Elixir and unquoted conventional lowercase Erlang atoms (including underscores and `@`); reject other identifiers with a diagnostic rather than inventing aliases or loading names globally. Verify each filename and manifest name against the BEAM's internal module identity, check the exported entrypoint and checksums, and assign each included module to exactly one source application. Compiler OTP and local tooling Elixir versions are *assumptions*, not certificates that an arbitrary libbeam build accepts a BEAM. OTP libraries are not silently bundled or promised available. Preserve dependency version metadata from the compiler's resolved app records; fail when it cannot be established instead of inventing a version.

Extend the existing BEAM import/opcode preflight to Erlang names and reject known host filesystem/network/NIF/on-load imports and native artifacts. Unknown imports, maps, process or OTP service usage must remain explicit provisional diagnostics. A zero-blocker report is only a static observation, not a libbeam load/execution proof. The current core eagerly resolves all module imports and can reject cycles even where stock OTP runs them.

## Stock-OTP to-do demonstration

Keep the guest worker and the **local HTTP host** in separate apps. The hybrid Mix worker implements request handling in Elixir and owns the mutable to-do list in an Erlang `gen_server`. The host starts that process on ordinary OTP and serves a loopback-only JSON API plus server-rendered browser UI; it communicates with the worker through the bounded binary wrapper. Create/list/update-or-complete/delete work during that host's lifetime; restarting it resets state. The example accepts at most 60 tasks with 160-byte UTF-8 titles, keeping worst-case escaped JSON within the 64 KiB response frame. The local host's HTTP libraries, templates and listener are **not** bundled as guest capabilities. Browser mutations need bounded input, a CSRF/same-origin check, and escaped output, but this local demonstration is not production hosting or an untrusted-code sandbox. Packer's worker artifact can include the Erlang state module for future handoff while marking its process/OTP imports and the Elixir facade unsupported or unresolved on today's libbeam.

The build/test prerequisite for standalone projects is a real `rebar3` executable; use a temporary downloaded executable for CI/local verification if needed, never modify the sibling libbeam repository. If that cannot be obtained safely, stop and ask rather than claiming an `erlc` imitation validated rebar3 support.
