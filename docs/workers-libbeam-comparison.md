# Workers architecture and Midgard's libbeam boundary

Research snapshot: 2026-10-11. This is an architecture comparison, not a claim that Midgard runs on Cloudflare or that libbeam can run an Elixir Worker yet. The OTP/libbeam checkout was read only; it has uncommitted changes and its APIs may evolve.

| Concern | Cloudflare's stack | Midgard's proposed counterpart | Status / boundary |
| --- | --- | --- | --- |
| Project creation | `create-cloudflare` (C3) / Wrangler project config | `mix midgard.new`, `midgard.config.exs` | Generator and target config implemented; builds remain local and provisional. |
| Language/API contract | `fetch(request, env, ctx)` returns `Response`; Request uses Fetch APIs; `env` supplies bindings, `ctx` handles invocation lifetime | Worker-facing `midgard` library defines request/response and a narrow byte-oriented entrypoint; host services become explicit brokered capabilities | `Midgard.Request` and `{status, body}` use a versioned binary wrapper on ordinary OTP, not Fetch parity or demonstrated libbeam execution. No `ctx.waitUntil`, streaming, fetch, or storage yet. |
| Dependency build | Wrangler bundles imported npm code by default with esbuild and can ship additional module types; `wrangler deploy --dry-run --outdir` inspects output | `packer` compiles and packages local/allowed dependency BEAM modules, manifest and target metadata; dry-run/inspect validates without executing | `<app>.midgard/` contains exact-name BEAM bytes and a bounded JSON manifest. Static checks reject known host-authority imports; unknown/profile requirements remain explicit. |
| Runtime and local test | `workerd` is the server/runtime (V8, Wasm, services, sockets and explicit bindings); Miniflare is a workerd-backed simulation used by tools | `libbeam` is the host-owned engine/isolate runtime; Midgard is a producer of bytecode and SDK contracts, not a replacement emulator | Selected-profile public Isolates, private loading, copied calls and reclamation now execute limited Erlang BEAMs; the stateful acceptance fixture still fails. Midgard's Elixir artifact has not loaded or executed there. |
| Deployment / routing | Wrangler deploys and configures Workers; workerd routes sockets to named services; Workers for Platforms adds dispatch namespaces and tenant routing | Future host adapter would own routes, Isolate lifecycles and byte invocations; Midgard artifact declares an entrypoint and requested capabilities | Midgard has no such adapter and removed the old loopback Phoenix/Realm host; building does not deploy. |
| Capabilities and security | Workerd config binds services/resources rather than granting ambient network; production Workers uses extra isolation layers | Compile-time SDK interfaces plus host-verified grants and bounded byte I/O; no OS handles or ambient network inside isolates | Capability grants need a separate host broker design. Neither workerd alone nor present libbeam is a hardened multi-tenant sandbox. |

## What the Cloudflare names mean

[`cloudflare/workers-sdk`](https://github.com/cloudflare/workers-sdk) is a monorepo containing [Wrangler](https://developers.cloudflare.com/workers/wrangler/), [create-cloudflare](https://github.com/cloudflare/workers-sdk/tree/main/packages/create-cloudflare), [Miniflare](https://github.com/cloudflare/workers-sdk/tree/main/packages/miniflare) and other tooling. `workerd` is a separate [runtime](https://github.com/cloudflare/workerd). `@cloudflare/workers-types` supplies TypeScript API typings; it is not the runtime. There is no public npm package named `@cloudflare/workers` in the registry at this snapshot (registry lookup returned 404). Midgard therefore maps to **multiple layers**: worker-facing types, C3-like generator, Wrangler-like packer/CLI, and an eventual host adapter; libbeam maps to the underlying runtime, not to all of workerd's HTTP and service layers.

Cloudflare's [fetch handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/fetch/) receives `request, env, ctx`. [Bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/) are both APIs and grants; a Worker does not need to hold their secret credentials. [Wrangler's bundling docs](https://developers.cloudflare.com/workers/wrangler/bundling/) distinguish inlined dependency code from separately uploaded modules. The [workerd README](https://github.com/cloudflare/workerd#readme) describes service/socket configuration, capability bindings and the fact that workerd alone is **not** a hardened sandbox. Reuse these separations, not its JavaScript semantics, brand, or a promise of feature parity.

## libbeam reality check and target

The checked-out OTP repo's [README](../../otp/README.md) and [two-isolate example](../../otp/libbeam/examples/two_isolates.md) say the Realm implementation was removed from active source. Its [selected-profile public Isolates](../../otp/docs/rfds/0003-public-isolates.md) now load/call/reclaim limited Erlang BEAMs. The [experimental C++ API](../../otp/libbeam/include/libbeam/engine.hpp) accepts host-supplied module bytes; the Isolate derives the module name from each BEAM, admits loading before `start`, and accepts bounded binary arity-one `start`/`call` payloads. This is a **limited runtime contract**, not an endpoint for the Midgard Elixir profile. Host paths and arbitrary Erlang terms are not part of that API. Two isolates should be able to load conflicting same-name modules without name rewriting. Artifact entrypoint metadata can hand a host a module/function name and bytes, but cannot call Isolates itself.

The [additive core profile](../../otp/libbeam/core/README.md) currently supports selected BEAM instructions, imports, literal forms and ordinary binaries. Maps, fun objects, PIDs, ports, refs and broad OTP services are not yet supported; even unused functions containing excluded instructions can cause admission failure. A normal Elixir struct (`%Midgard.Request{}`) and JSON/Jason usage imply maps and wider dependencies. **A Packer artifact may be structurally valid while still unexecutable on today's libbeam.** A static validator must report structural safety checks separately from an explicit *provisional* future-Isolate profile. It must not certify execution merely because `:beam_lib` accepts the modules. The existing 64 KiB call/result target is distinct from artifact size and heap/CPU budgets.

## Decisions for this repository

1. Produce exact-name BEAM files and a manifest; do not rename tenant modules globally or load BEAMs into the Midgard host during build/inspection.
2. Keep worker SDK, generic Packer, Midgard-specific CLI/generator and eventual host capability interface distinct. Do not add fake network/storage bindings just to resemble Cloudflare.
3. Make no libbeam call in this artifact-only project. Demonstrate deterministic assembly, inspection, static rejection and representative pure-Elixir compilation on ordinary OTP; label this worker's libbeam runtime validation pending.
4. Treat native/NIF screening and static import/opcode checks as conservative compatibility checks, not a security proof. Unknown or unsupported capabilities must be reported rather than silently admitted.

Local links above resolve against the sibling `otp` checkout in this workspace; on GitHub, see the [libbeam repository documentation](https://github.com/leostera/otp/tree/main/libbeam) and its [RFDs](https://github.com/leostera/otp/tree/main/docs/rfds). The OTP checkout was not modified for this research.
